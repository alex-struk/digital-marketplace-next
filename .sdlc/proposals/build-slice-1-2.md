# Does slice 1 (A visitor can read the service's own pages) do what its criteria say?

**Recommendation.** This was a revision with one named condition, and I treated it as one: the sandbox identity provider never came up, so the run stopped there and none of slice 1's criteria were reachable.

This was a revision with one named condition, and I treated it as one: the sandbox identity provider never came up, so the run stopped there and none of slice 1's criteria were reachable. I changed nothing else in the application.

**What was wrong.** `app/compose/idp/realm-template.json` opened with a `"_comment"` array — eleven lines of prose explaining what the realm is for, who the accounts are, and why the password is a placeholder. Keycloak deserializes that file straight onto its own `RealmRepresentation`, and that class is not marked as tolerating unknown members, so the key was not ignored: it aborted the import, and the import aborting took the server down with it. With `restart: unless-stopped` the container came back, read the same file, and died the same way, which is the restarting state the ruling saw. The two log excerpts are one minute apart and identical, and both name `_comment` as the field — the failure was deterministic and had nothing to do with the realm's substance.

**What I did.** I removed the key. The prose it held was worth keeping, so it now lives in a new `app/compose/idp/README.md` beside the template: the accounts and that each signs in with its `idp_id`, the password placeholder and why no password is written into the repository, what `identity_provider` records and which slice will read it, and the client's shape. The README leads with the constraint itself, so the next person to want a note in that file learns why they cannot have one.

**Two adjacent hazards I closed while I was there.** The renderer was a `sed` substituting the password as plain text into a JSON string. A password containing a quote or a backslash would have produced a realm file Keycloak could not parse — the same fatal shape of failure, from a different cause, and one nobody could have predicted from the repository since the password only exists in the environment. `app/compose/idp/render-realm.mjs` now does the substitution with JSON's own string escaping and then parses the result before writing it, so a realm that cannot be read fails the one-shot render service with a plain message instead of sending the identity provider into a loop. It runs on `node:22-alpine`, which every other image in the file already builds from, so this costs no extra pull and drops the `alpine:3.20` one. I verified the substitution against the real template with passwords carrying quotes, backslashes, pipes, ampersands, dollars, tabs, newlines and non-ASCII characters: all parse, and each round-trips to exactly the password given.

**The guard.** I could not run Docker in this session — the commands needed approval that was not available — so the fix rests on reading the failure rather than on watching it pass. That made it worth putting the invariant somewhere `check` reaches. `app/backend/tests/sandbox-composition.test.ts` reads the compose file and the realm template as files and asserts: no key anywhere in the realm begins with `_` (with a negative case proving the walk would actually find one, so the test cannot pass vacuously); every top-level realm key is a `RealmRepresentation` member, from a deliberately narrow list a later slice extends once it has checked a spelling; every account has a slug username and exactly one credential; the placeholder appears once per account and no literal password appears; port 3000 is published by `frontend` and by nothing else; 8080 is published by `idp` alone and its server is told to listen there; and `idp` waits on the render service completing successfully, so it cannot come up with accounts nobody can sign in as. It lives in the backend package because that is where a test can run without adding a workspace, which would have desynchronised `package-lock.json` and broken the installed-from-lock builds.

I deliberately did not add a healthcheck to the identity provider. The right readiness signal is the realm endpoint, the harness polls that address itself, and the Keycloak image has no HTTP client to probe with — a healthcheck I could not execute here would be a new way for the run to stall, not a safeguard.

**State.** `npm --prefix app run check` passes: typecheck across all three workspaces, 93 unit tests (15 migrations, 47 backend, 31 frontend). The slice's own criteria — R-7.1, R-7.2, R-7.3, R-7.4, R-7.12, R-7.17, R-7.18, R-7.19 — are untouched from the returned proposal; the header and footer, the home shell, the three learn-more screens and their service level agreement link, `/content/:slug` with formatted text that never executes markup, the not-found screen, and the seeded fixed pages all stand as they were, and the backend's `the-service-answering.test.ts` still exercises them end to end over a real schema. What I cannot claim is having seen the composed stack answer on port 3000 or the realm endpoint answer on 8080; that verification belongs to the run after this turn. If something beyond the identity provider is also wrong, it will surface now that the run gets past the wait it was stuck on.
