**Condition 3 — the two accepted criteria with neither test nor ledger entry.** I took the first option and raised the spec change rather than only recording the gap. `spec/domains/users.md` now carries `- state: obsolete` on R-4.10 v1 and R-4.11 v1, in place of `accepted`; nothing else in either block changed, and each already carried the `superseded-by` and the explanatory note that say why.

I chose obsolescence over a ledger entry deliberately, and the reasoning is worth recording because it differs from how the other two superseded criteria in this domain were handled. R-4.7 and R-4.15 also sit at `accepted` under a `superseded-by`, and both got not-testable entries, because both are genuinely out of the surface's reach. R-4.10 and R-4.11 are not out of reach — they are contradicted. R-4.11 says the person is told they reactivated the account themselves; R-4.20, which replaces it, says they are told an administrator did, and the test already written for R-4.20 asserts exactly that wording and asserts the absence of R-4.11's. R-4.10 says the reactivation control is offered for a self-deactivated account and the service refuses it; R-4.19, which replaces it, says the control should not be offered at all. Deriving tests for the superseded pair would put two assertions in the suite that cannot both pass, and filing them as not-testable would be false, since the reach exists. Leaving them accepted was the only remaining option and is the state the reviewer flagged. Obsolete is the honest resting place for a defect criterion whose correction has already been accepted.

Two consequences the next stage owns. `spec/spec.md` and `spec/criteria-index.json` are generated by `sdlc run ratify` and are not to be hand-edited, so both still show R-4.10 and R-4.11 as accepted; ratify has to be re-run for the generated view to agree with the domain file, and I did not run it. And if any gate counts accepted criteria against tests-plus-ledger, its arithmetic for the users domain changes by two.

**Condition 4 — the R-4.3 known-red, carried forward.** Naming it here as the reviewer asked, so it does not live only in a file comment. This is a seed gap, not a surface gap, and it belongs to whichever stage owns `tests/seed/manifest.yaml`. The manifest holds exactly one account with `accepted_current_terms` false, `vendorWithTermsReset`, and that state is one-shot: the first test in a run that agrees to the terms on its behalf consumes it for everything after, and nothing restores it for a single account. Three files draw on it — R-4.23 reads without consuming, R-4.24 consumes, R-4.3 reads and then consumes. The suite runs single-worker with parallelism off, and default path ordering puts `R-4.24.spec.ts` before `R-4.3.spec.ts`, so R-4.3 finds the account already agreed and its first two tests fail on the fixture rather than on the behaviour they describe. The remedy is a second vendor account with its agreement withheld, so each consuming file gets its own one-shot state, or a reseed between files. The tests are deliberately not marked as expected failures: that would silence a real regression in the same breath. Until the seed changes, those two tests are red in a full run and green when the file runs alone against a fresh database.

**Surface gaps still open in this domain**, restated for whoever extends the contract next, since every one of them is why a criterion has a ledger entry instead of a test.
