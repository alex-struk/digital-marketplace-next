# Do the revised evaluation tests now follow from their criteria and from nothing else?

## Journal

**Condition 1 — R-5.22's decimal-places test.** The reviewer offered two ways out, and I took the first: the test no longer names `scoreOutOfRangeError()`. It now enters 4.125 *and* a valid comment, then asserts `evaluationIndividualListSwu.submitDisabledUntilComplete()`. That observation makes no claim about why the entry was refused, and it is the contract's slot for the criterion's own second clause — "the evaluation cannot be submitted until every question has a score in range and a comment". Supplying the comment is what makes the assertion discriminating rather than vacuous: with the comment present, the only thing that can leave the question short is the score having been turned away. A short comment in the file records that reasoning.

I deliberately did not take the second option — splitting the decimal half into `not-testable.yaml`. Across the whole suite there are 114 spec files and 61 not-testable entries, and the intersection is empty: no criterion id currently appears in both places, and the suite's own README states the convention as an entry "instead of a file". R-5.22 is largely testable — the out-of-range half, the empty-comment half and the submit-blocked half all run through the surface — so recording `id: R-5.22` as not-testable would have created the suite's first id-in-both-places contradiction and would have misrepresented a criterion that is mostly reachable. If whoever rules this prefers the split anyway, that convention question should be settled first, because it affects how a partially-reachable criterion is recorded everywhere, not just here.

**Condition 2 — R-5.19's second test.** The `emptyPanelOpportunitiesMessage()` assertion is gone. The test now ends on the `not.toContain(TITLE)` line, which is the whole of what the criterion says about the unrelated employee.

**Condition 3 — the typecheck.** I could not run it. `npm install` is refused in this environment exactly as it was in the last one; `tests/node_modules` does not exist and there is no global TypeScript to fall back on, so `npm run typecheck` has nothing to run against. Per the condition I am not offering a substitute: no symbol cross-check, no manual resolution pass, nothing standing in for `tsc`. The typecheck over `tests/acceptance/evaluation/` remains genuinely unrun, and it has now been unrun across two consecutive rounds for the same reason. Who can run it: whoever administers this pipeline's execution environment — the check needs a stage or a machine with network access to the npm registry, or a workspace pre-seeded with `tests/node_modules`. It cannot be closed from inside a spec-only workspace, and it will keep coming back unmet until that changes. My two edits are small and use only symbols already exercised elsewhere in the same directory, but I am not claiming that as evidence of anything.

**Condition 4 — the sweep for the same pattern.** I read all 25 evaluation specs against their criteria in `spec/domains/evaluation.md` and found no third instance. The distinction I applied: an assertion is over-reaching when it uses a surface observation named for a *different* rule than the one the criterion states. That is what made the R-5.22 case wrong — 4.125 sits squarely inside a five-point range, so `scoreOutOfRangeError` names a rule the scenario does not break, and the page carries no slot for the rule it does break. By contrast, several tests do name a specific observation, but in each case the observation's name is the criterion's own rule restated: `panelLockedAfterConsensus` for R-5.16's "fixed from the consensus stage onwards", `chairOnly` for R-5.29's "only the chair may record", `ownEvaluationsOnly` for R-5.28's "no one but the evaluator who wrote them", `visibleToEvaluatorsOnly` for R-5.34. Those I left alone. Several others name an exact message because the criterion itself quotes that message — R-5.3, R-5.25 — or because which message appears *is* the rule under test, as in R-5.10 and R-5.12. Refusals and absences elsewhere are asserted neutrally with `toBeFalsy()`, which is what the criteria ask for.

The closest call was R-5.13's first test, and I want it on the record rather than silently resolved. R-5.13 says only that finalising "must be refused"; the test asserts `notAllConsensusesSubmittedError()`. That does pin a rejection identity the criterion does not name, and the message it corresponds to belongs, per R-5.4, to a different rule about draft consensuses. I left it because the observation is a contract slot rather than a literal string, and "not all consensuses have been submitted" is a true and directly implied description of a proponent who has no consensus at all — unlike "out of range" for a value inside the range. That is a judgement call, and a reasonable reviewer could rule the other way; if so, the fix is one assertion, and the neutral evidence is already present in the file's second test.

**One environment note.** This run's workspace is not a git repository — there is no `.git` and no copy of `main` — so I could not verify my own changes by diff and relied on file timestamps instead. That is a fact about the workspace I was given, not a dispute with the correction in the rationale, which concerned a different environment.

**No new surface gaps.** Neither condition required reaching for something the contract does not name, so I have nothing to add to the list of missing actions or observations from the previous round. The one gap these conditions confirm is the one already named: the evaluation-individual-create pages carry no observation for a score refused on its number of decimal places, only `score_out_of_range_error` and `empty_notes_error`. Until the contract gains one, R-5.22's decimal clause can be tested only through its downstream effect on completeness, which is what it now does.
