One condition per line, and exactly one of these forms:

- `defect-in-old <ID>` — the old application really does fail this and the criterion is right
  anyway. The test stands as written and the rebuild has to pass it; the criterion keeps a note
  saying so. No text after the ID.
- `spec-wrong <ID>: <corrected statement>` — the criterion misdescribes what the old application
  does. The statement is replaced and its version bumped, which marks the test stale so
  `derive-tests --stale` writes it again from the corrected criterion.
- `test-wrong <ID>: <why>` — the criterion is right and the test is not. The id goes to
  `tests/acceptance/redo.yaml` for `derive-tests` to redo, still blind, and `<why>` records what
  the test got wrong without describing how the application is built.

The ID is the criterion's own id exactly as `spec/criteria-index.json` spells it. `defect-in-old`
takes no text; the other two require a colon and text on the same line. A condition may not span
more than one line.


## Ruling

**Verdict:** return
**By:** agent:product-owner

The question is whether each of the 40 listed failures (of 173) is the old application's fault, the criterion's or the test's. Ruling: return, with no criterion ruled, because almost none of the failures is any of those three. They come from the old-target adapter, the layer that turns a test's steps into actions and reads against localhost:3000. None of the three calibration verbs describes an adapter fault. Ruling defect-in-old would make adapter bugs obligations for the rebuild, and ruling test-wrong would send sound tests back for a blind rewrite that hits the same adapter. The evidence: (1) contentView.pageTitle is bound to the browser tab title (tests/adapters/old/index.ts:2714), which the old app suffixes with ' — B.C. Digital Marketplace', so R-7.1, R-7.4 and the signed-out case of R-7.10 compare 'About us' with 'About us — B.C. Digital Marketplace' while the tests are correct. (2) The adapter reports 'no control labelled' for 'Save Draft', 'Deactivate Account' and 'Add Team Member(s)', yet all three are rendered by the old source (opportunity/code-with-us/create.tsx, user/profile/tab/profile.tsx, which hides deactivation only when an administrator views their own profile, and organization/edit/tab/team.tsx). Save Draft is missing even for public sector staff (R-1.8), who are allowed to use it. The same lookup fault causes R-1.7, R-3.7, R-3.8, R-3.9, R-4.5, R-4.9 and R-6.10, and the missing opportunity id in R-5.1, R-5.9 and R-1.9. (3) Reads return the wrong shape or nothing: organizationList.organizationName returns only the first row (R-3.1), opportunityList.unpublishedGroup returns a count '36' instead of titles (R-1.3), and saveDraft leaves drafts 'Untitled', so the title is never entered (R-1.3, R-1.9). fileUpload.storedFileIdentifier yields no id (R-8.7, R-8.10), and the Sprint With Us and Team With Us create flows never reach the panel step (R-2.10, R-2.11).
