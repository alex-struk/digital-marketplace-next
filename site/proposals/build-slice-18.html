How the consensus is stored and answered. It lives in the existing schema's chair tables, kept under the chair's account. It has the same shape as an individual evaluation: a list of DRAFT/SUBMITTED status rows and one row per question. The seed writes it the same way. The four contract addresses (start, read, change, list) answer in the same shape as an individual evaluation, with the chair as the panel member. The code is in backend/src/evaluations/ (consensus.service.ts, prisma-consensus.store.ts, consensus.controller.ts), and the rules are in backend/src/rules/consensus.ts, which the screens also import. Reading and writing these tables is now shared with the individual evaluation store rather than copied.

What each criterion does in the application:

  • R-5.29, R-5.30 (recording): only the chair records, only at the consensus stage, one consensus per proponent. A second one gets a 409 worded the same way as the individual-evaluation duplicate. Anyone else, and the chair once the stage is over, gets a 401. A submitted consensus can be changed and stays submitted.
  • Submitting the set (R-5.13, R-5.31): the chair uses the submitConsensusQuestionEvaluations tag from the Consensus tab, after a confirmation dialog. It needs a complete consensus for every proponent still being evaluated on the questions. The owner and every active administrator are then emailed.
  • R-5.12, R-5.28 (reading): an administrator can read the consensus at any stage. The panel can read it from the consensus stage. An owner who is not on the panel sees the explanation message instead of an empty list.
  • R-5.28 (individual evaluations): the rules from slice 17 are unchanged. The consensus create page is the missing page to everyone before consensus. From consensus on, the chair gets the form with every evaluator's scores beside their names. Other panel members see the same scores read-only, with a notice that only the chair records the consensus.
  • R-1.41, R-1.50, R-5.10, R-5.13, R-5.14 (finalising): the finalizeQuestionConsensuses tag is the only way out of the stage. "Finalize consensus scores" in the manage page's action bar is offered to the owner and administrators, not the chair. It is refused with "Not all consensuses have been submitted." or with the no-screenable sentence, which names the Code Challenge for Sprint With Us and the Challenge for Team With Us. The refusal is shown in the shared refusal alert, with an inner test ID saying which refusal it is. The older startCodeChallenge and startChallenge actions are refused while at consensus.
  • R-2.29, R-5.32, R-5.33 (what finalising does): in one transaction it writes a history row on every proponent ("Team question scores were entered. Q1: 5; …"). The best four (Sprint With Us) or three (Team With Us) that met every minimum move to the next review stage. The opportunity moves to the code challenge or the challenge. The chair and owner are emailed.
  • R-5.36: both programs go through the same code.
