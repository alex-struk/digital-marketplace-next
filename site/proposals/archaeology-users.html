Journal

The users domain is the account layer under everything else the service does. Nobody registers an account by hand: the first time a person signs in through the identity provider an account is created for them, and the identity they used fixes what kind of account it is — a government identity makes a public sector employee, a code-hosting identity makes a vendor, and an administrator is only ever a public sector employee promoted by another administrator. From there the domain governs the profile a person keeps (name, email address, job title, picture, notification preference, and for vendors the capabilities they hold and their acceptance of the service's terms), who may read or change whose record, and the account's movement between active and two distinct inactive states — deactivated by its owner, which reverses itself on the next sign-in, and deactivated by an administrator, which locks the person out until an administrator reverses it.

Sources disagreed in four places, and I recorded each rather than picking a winner. Two are front-end against back-end within the code itself: the service accepts a profile change from an administrator against somebody else's account while the interface deliberately suppresses the form, and the service answers an ordinary public sector employee's request for the list of every registered person while the interface shows them a missing page — that list carries everyone's email address and status, so the wider reading discloses more than the interface ever intended. Both are marked open / conflicting, because which way to resolve them is a decision rather than a finding. Two more are documentation against code: the published interface description gives the profile-update operation a request method the service does not accept and describes deactivation as producing a single "Inactive" state when there are really two that behave differently; and the application's own README describes a shared-token facility for overriding accounts and sessions, whose configuration setting is read but for which no route is assembled anywhere in the application — recorded as documented-only, since the source cannot say whether the feature was removed or merely anticipated.

Three defects are recorded that should not carry forward, none with a replacement written, because each needs a ruling rather than an obvious fix. The interface offers a "Reactivate Account" control for every inactive account without distinguishing the two kinds of inactivity, so an administrator is invited to perform an action the service will always refuse for a self-deactivated account. A person whose account an administrator reactivates is told that they themselves reactivated it — a correctly worded message exists, appears in the service's internal notification preview, and is never sent. And the application carries direct sign-in routes for fixed test accounts, enabled outside production, which create a session without consulting the identity provider and without checking whether the account is active; they are a test-only entrance of exactly the kind this project forbids, and they are also how the pipeline currently signs in against the old application as an oracle, so any test of "a deactivated account cannot sign in" cannot use them. I flagged that explicitly on both the criterion and the new persona.

What I could not determine: whether a newly created public sector employee is meant to skip the profile-completion step. Every new account is redirected to that page, but the page admits vendors alone and sends everyone else straight to the dashboard, so a public sector employee is never asked to confirm their details and never sees the notification choice offered there — the code shows the outcome but not the intent, so it is noted rather than resolved. I also could not settle from the source what a person actually sees when a save fails because two accounts of the same kind would share an email address; the constraint is real and enforced in the stored data, but the failure surfaces as a generic sign-in or save failure indistinguishable from any other fault. Finally, the domain introduces no genuinely new role — vendor, public sector staff and administrator were all already listed — so the only persona I added is deactivated-vendor, which is an account state rather than a role, added because none of the existing personas can reach the sign-in rules this domain turns on. I left the sixteen existing persona entries untouched.

The question is whether this is what the users domain does and which of it is the contract. Approve. I read the code behind the load-bearing rows this session and every citation I checked resolved where the criterion said it would, and the grading is honest rather than generous: most rows sit at inferred on code alone and archaeology declined to write corrected criteria for its three defects on the correct ground that choosing between widening a permission and hiding a control is my decision, not its finding. I am confirming three criteria, each with a stated reason rather than to keep things moving. D-users-2, D-users-7 and D-users-8 all rest on the same block at src/back-end/lib/routers/auth.ts:490-507, where the welcome mail is a literal 'if (user && user.email)', the self-deactivated account is flipped to Active and sent accountReactivatedSelf, and the admin-deactivated account falls to 'makeAuthErrorRedirect(request); return null' - three single-sited branches in one function that leave no second reading. I am deciding both conflicts rather than passing them on, and in both cases toward the narrower reading, because in both the interface is the half that states an intent and the service is the half that inherited a shared helper. On D-users-14 the front end suppresses the form twice under the comment 'Admins can't edit other user profiles' at profile.tsx:469 and :626, while permissions.ts:163 is the same 'own account or admin' expression the deactivation rule at :167 needs for its own reasons - the permission is wide because it is shared, not because anyone decided an administrator should rewrite somebody's name. On D-users-25 the disclosure decides it: permissions.ts:152 admits Government alongside Admin, list.tsx:296 admits Admin alone and the navigation link is offered to administrators alone, and the list carries every registered person's email address and account status, so platform article P3 makes answering an ordinary public sector employee the reading to close rather than the one to adopt. D-users-21 is confirmed as a defect on a count rather than a reading: accountReactivatedAdmin is defined at mailer/notifications/user.tsx:144 and called nowhere in the repository, its template appearing only in the admin notification preview at routers/admin/index.tsx:164, while resources/user.ts:310 sends the self-reactivation wording; the fix is to send the message that already exists. D-users-20 I am ruling toward hiding the control rather than widening the service, because a self-deactivated account already reverses itself on the next sign-in, so an administrator reactivating one adds nothing the person cannot do themselves and the honest fix is to stop offering an action the check at resources/user.ts:248 will always refuse. Two rows leave the contract entirely. D-users-29 is obsolete under constitution article J3, which forbids test-only entrances outright; the recovered statement is also wrong about scope, since /auth/createsessiongov, /auth/createsessionadmin and /auth/createsessionvendor/:id are each gated on NODE_ENV being exactly 'development' rather than on being outside production, and I will not confirm a statement I know to be inaccurate in order to mark it a defect. D-users-32 is obsolete because the feature does not exist at all - SERVICE_TOKEN_HASH occurs exactly twice in the old repository, its definition and its README row - so the criterion records that the old documentation is stale rather than a behaviour the rebuilt system must exhibit, which is the same reason D-opportunities-51 was withdrawn at G1; a shared token overriding accounts and sessions would be a J3 test-only entrance in any case. D-users-4 I am spiking rather than answering, because whether a public sector employee is meant to skip profile completion is a product decision and archaeology was right that the code shows the outcome and not the intent. Everything else stands exactly as recovered. Four corrections that do not warrant a return but must not be lost: the journal says twelve surface pages where ten were appended and sixteen existing personas where personas.yaml holds eight, which is the second archaeology narrative in a row to miscount its own output and matters because the counts are what a gate holder uses to check the artifact against its description; D-users-5's note cites D-users-25 for the withdrawal of standing terms acceptance when it means D-users-27; the deactivated-vendor persona should carry session-route: null rather than { role: vendor }, because the old application's session route creates a session without checking account status, so a test signing in that way would pass while proving nothing about D-users-7; and the sandbox fixture vendor-deactivated-1 does not exist in the seed data, which the stage that builds the seed data owns. Not escalating: the tier is STANDARD, the stage reported no confidence shortfall, and the readings that were genuinely ambiguous are per-criterion with an established mechanism for ruling them. What would change this ruling: evidence that an administrator was deliberately meant to edit another person's profile, which would turn D-users-14's replacement from a permission narrowing into an interface widening; a second registration of the user list route with a different permission rule, which would change what D-users-25 is actually disclosing; or any citation that does not resolve at the pinned commit.
