Calibration conditions

One condition per line, and exactly one of these forms:

  • defect-in-old <ID> — the old application really does fail this and the criterion is right anyway. The test stands as written and the rebuild has to pass it; the criterion keeps a note saying so. No text after the ID.
  • spec-wrong <ID>: <corrected statement> — the criterion misdescribes what the old application does. The statement is replaced and its version bumped, which marks the test stale so derive-tests --stale writes it again from the corrected criterion.
  • test-wrong <ID>: <why> — the criterion is right and the test is not. The id goes to tests/acceptance/redo.yaml for derive-tests to redo, still blind, and <why> records what the test got wrong without describing how the application is built.

The ID is the criterion's own id exactly as spec/criteria-index.json spells it. defect-in-old takes no text; the other two require a colon and text on the same line. A condition may not span more than one line.

Ruling

approve by agent:product-owner (persona agent) on 2026-09-14 19:42.

The question was whether the three criteria still failing against the old application, R-8.1, R-6.23 and R-6.28, fail because of the application, the spec or the test. Ruling: approve, with test-wrong on all three, because in each case the evidence shows the old application doing what the criterion says and the test assuming something the criterion never states. R-6.23 and R-6.28 both poll vendor.one first and both failed after about 11 s, which is a single 10 s poll timing out on that first vendor. The R-4.19 test signs in as vendor.one and deactivates the account. It relies on signing in again to restore it, which the suite's test sign-in does not do, and calibrate-triage-old-2 recorded vendor.one's profile as already offering only reactivation. Both criteria promise a message only to active vendors, so a deactivated vendor receiving nothing meets them. The same snapshots show the Vendors Notified confirmation, and the old code sends one message per active vendor and never lets a failed send interrupt the loop (email-notifications.ts:76, terms-updated.tsx:11, transport.ts:24-68). For R-8.1, the old code grants upload on being signed in alone (permissions.ts:326, file.ts:131). The read-access statement the test sends passes the service's own validation, and the uploader's seeded account exists with that identifier. The same persona uploading through the same path passes R-8.2, whose read-access statement is the plainest one, and calibrate-triage-old-1 recorded this signed-in test passing in an earlier run. Nothing points at the product, and the test makes success depend on a read-access detail R-8.1 never mentions. Caveats about the evidence: no test that waits for mail has yet passed against the old target, so delivery to the catcher is still unproven, and a direct query of the catcher and the database was not run. The old application also composes a message with no recipient for a vendor who holds no email address, which R-6.28 forbids, but the current test does not observe that and it is not what failed. Separately, the test suite's owner should note that the R-4.19 test leaves vendor.one deactivated on the old target. What would change this ruling: a rewritten R-6.23 or R-6.28 test that establishes its vendors are active and still finds no message reaching them would make that criterion defect-in-old. A rewritten R-8.1 test with the plainest read access that is still refused while signed in would do the same for R-8.1.

Conditions

  1. test-wrong R-8.1: the signed-in half makes a successful upload depend on a read-access statement naming one particular account, which R-8.1 never mentions; state read access in the plainest form the spec offers, so that being signed in is the only thing that differs between the two halves
  2. test-wrong R-6.23: the test expects a message for vendors it assumes are active without establishing that they are active when the announcement is made, and the first one it polls is an account another test in the suite leaves deactivated; the criterion promises a message only to active vendors, so establish the active and deactivated vendors the given names before announcing and check each group against what the criterion says it should receive
  3. test-wrong R-6.28: the test polls vendors it assumes are active without establishing it, the first being an account the suite leaves deactivated, so one timeout ends the check before any other vendor is looked at; establish that every vendor polled is active at the moment of the broadcast, keep the vendor holding no email address among the recipients, and report every addressable vendor not reached rather than stopping at the first
