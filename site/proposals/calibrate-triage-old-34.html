Question: which of R-1.1, R-1.17, R-2.19 and R-5.25, all failing against old, did this project's adapter cause? Ruling: approve, with three adapter-wrong and one product-question. These rows were carried over from run 2026-09-30-8 and have no snapshots, so I read each failure's error text against the test and tests/adapters/old/index.ts. R-2.19: in every refusal case the service's message is correct ('inception phase phase: This opportunity does not require this phase.', 'prototype phase phase: This opportunity requires this phase.', 'implementation phase members #1 members: You may only specify a single scrum master.'). But refusalByField (index.ts:10127) names phases through REQUEST_FIELD_NAMES in lowercase ('inception phase'), and the test finds the phase's entry with a case-sensitive \bInception\b, so it never finds the message. That is the adapter reading the right answer and reporting it under the wrong name. R-2.19's 'no scrum master' clause is a different kind of failure: the service answered 201 SUBMITTED with no member of the implementation phase marked scrum master, so the application accepted it. It will come back as a product question once the binding is fixed. R-5.25: submitDisabledUntilComplete returns controlState's 'enabled'/'disabled'/'absent' (index.ts:609 and 7410). All three are truthy, while the test reads truthy as 'submission is not offered'. The enabled control was reported as withheld, and the sibling 'not offered' clause passes whether or not the control is enabled. R-1.17: opportunitySwuEdit.teamQuestionsTab (index.ts:3561) opens the sidebar's 'Team Questions' tab. The received text shows that tab sits under OPPORTUNITY EVALUATION: it is the proponents' scoring table, not the opportunity's list of questions, which lives under the 'Opportunity' tab. So the position clause read a screen that never lists the questions. R-1.17's other two failures (a 1,001-character question and a 101st question not refused) go through the same addQuestion/fieldError path as the guideline, score, word-limit and minimum-score clauses, which pass. They look like the application's and will come back once the tab reader is fixed. R-1.1: the closure itself works, because the stage and proposal-review clauses pass. The failing clause is the panel announcement, read by the shared mail fixture rather than the adapter. Nothing points at the binding, which matches the earlier product-question ruling. Tier is STANDARD and no residual risk is marked unaccepted, so nothing escalates. What would change this: if a corrected binding reads the phase-named refusal, the control's real state, or the opportunity's own question list and the check still fails, that failure is the application's and goes to the product owner.
