Journal

The notifications domain is the old application's only way of reaching a person who is not currently looking at it, and it has exactly one channel: an email message the service composes itself, in a house layout, and sends either to one person or as a broadcast to many. Every notice in the service — an opportunity published, a proposal awarded, a team request made, terms changed — passes through the same small piece of delivery machinery, which decides whether messages are sent at all, marks them when the environment is a test one, splits large audiences into batches, and swallows every failure. Over all of that a person has precisely one control: a single choice to be told about newly published opportunities, set at sign-up, changed either from their notification settings or from a shortcut on the opportunity list, and reachable from the unsubscribe offer at the foot of every message the service sends.

I deliberately did not re-record which event notifies whom — the opportunities, proposals, organizations, evaluation and users domains already carry that, and one of my early findings (a decline link in a team-request message pointing at a page that does not exist) turned out to be recovered and already superseded in the organizations domain, so I dropped it rather than report it twice. What this file adds is the machinery underneath, the preference over it, the two service-wide broadcasts that belong to no other domain (changed terms, and the administrator's preview page), and the shape of individual messages where that shape is itself a decision.

What conflicted. One straight contradiction between prose and code: the README says an administrator can preview all email notifications on an internal reference page, and the page shows fifty of the sixty-two messages the service can actually send. The twelve missing are the pair sent when a Code With Us opportunity goes for review, and every message the evaluation panel machinery introduced — panel named, panel altered, ready for consensus, consensus submitted, consensus finalised, in both programs that have panels. The pattern fits a page that was kept current until panels arrived and then was not, but the source cannot say whether that is oversight or a deliberate narrowing, so I graded it open and left the ruling to a human. A softer conflict: the message announcing changed terms tells vendors they must accept before submitting to two of the three programs, while the service in fact refuses a submission to all three without a current acceptance — stale copy that misleads the reader about Team With Us specifically. And a quieter inconsistency inside the code itself: batched sends normally hide recipients from one another, but four notices in the evaluation sequence put the whole batch in the visible address line instead, so panel members and opportunity owners see each other's addresses. Everything else the README documents — the switch that disables notifications, the test marking, the batch cap of fifty, the sender address — agrees with the code exactly, and those are the criteria I was able to grade confirmed. The published interface description covers the notification preference and both watch actions but is silent on the terms broadcast, which therefore has no second source at all.

What I could not determine. What happens when the service tries to notify an account that holds no email address. Accounts without one are allowed on purpose, and most messages guard against it only by substituting an empty recipient list — the message is still composed and still handed on to be sent, so the outcome is decided outside the application's own code, and because delivery failures are only written to an operational log and never surfaced, nothing inside the service would reveal which outcome occurred. It matters most for the terms broadcast, which walks every active vendor one at a time: whether one address-less vendor stops the run for everyone after them is exactly the question the source cannot answer. I recorded it as open with the question a human needs to rule on. Two further things I could describe but not settle: whether the four notices that disclose their recipients should be corrected (the rest of the code's own behaviour says yes, but nothing states it), and whether the single notification preference is meant to govern only new-opportunity announcements — the settings page is honest about its scope, but every other message still ends with an unsubscribe offer that leads to a choice which will not stop messages of that kind, and no source says whether the other kinds were ever intended to be declinable.

Ruling

approve by agent:product-owner (persona agent) on 2026-09-07 05:01.

The question is whether this is what the notifications domain does and which of it is the contract, and the ruling is approve: twenty-one criteria over the delivery machinery, the single preference above it and the two service-wide broadcasts is the right cut, and deliberately not re-recording which event notifies whom keeps this file from contradicting the five domains that already own that. Three rows I confirmed because the cited code leaves no other reading, not because I wanted them moved. D-notifications-2 is settled by transport.ts:34-58, where the send callback logs the failure and calls resolve() unconditionally under the comment 'Do not reject promise, only log the error', with makeSend swallowing composition failures the same way, so nothing anywhere can observe a message that was never delivered. D-notifications-5 is settled by transport.ts:30, where text is convert(params.html, {wordwrap: 130}) and no notification anywhere sets text itself, so the plain-text form has exactly one possible origin. D-notifications-7 is settled by templates.tsx:414 hardcoding users/me?tab=notifications&unsubscribe against VIEWER_USER_ROUTE_PARAM = 'me' at user.ts:6, which profile/index.tsx:81 resolves to viewerUser.id and whose fail branch at :93 redirects an unauthenticated reader to sign in and back — the link carries no recipient identity at all, so it can only ever act on whoever is signed in. Two I reworded rather than confirmed, because the behaviour is right and the sentence is not: D-notifications-4 asserted that a reply 'reaches nobody', which is a claim about a mailbox outside the application and not something the source can support, where what the code does establish — one configured sender, a do-not-reply address, no reply-to header — is both provable and the part the rebuild has to honour; and D-notifications-6 said every message ends with a way to stop receiving notifications, which overstates a link that stops only new-opportunity announcements, and the precise wording matters because D-notifications-10 turns on exactly that gap. Five rows I ruled as defects rather than sending them back, because each is a decision this persona owns and archaeology has already gathered everything the source can give. D-notifications-19 I promoted from open on a hard count rather than on the README's word: 62 sender functions exist under mailer/notifications and the reference page calls exactly 50 of them, and the 12 absent are precisely the pair named in the criterion plus every panel and consensus notice, so whether the omission was oversight or narrowing does not change that a page an administrator uses to check copy before an event is silently incomplete, which is the failure the rebuild must not inherit. D-notifications-9 is confirmed by count as well — eight sites put the batch in the visible line against ten that blind-copy it, all in the same files by the same authors — and the service's own overwhelming practice is the answer to whether panel members should see each other's addresses. D-notifications-16 is a straight disagreement I verified on both sides: terms-updated.tsx:40 names Code-With-Us and Sprint-With-Us, while hasAcceptedCurrentTerms gates submitCWUProposal at permissions.ts:581, submitSWUProposal at :838 and submitTWUProposal at :1375 alike, so the message misleads a Team With Us proponent about a rule that will refuse their submission. D-notifications-14 is confirmed at db/user.ts:161-165, where the announcement list filters whereNull('deactivatedOn') and the watcher query at subscribers/code-with-us.ts:66-81 filters neither deactivation nor preference; mailing an account that cannot sign in to act is not a behaviour to carry forward, and I am ruling for suppressing delivery while keeping the watch, which matches how the preference itself already works. D-notifications-10 I defected only on its narrow half — a footer labelled Unsubscribe that will not stop the message it is printed on — and left the wider question of which notices become declinable to the rebuild's own intent, because that is new design rather than recovered behaviour. D-notifications-21 I spiked rather than decided: the criterion as written is a statement that the old system's behaviour is unobservable, which is honest and correct, and confirming a non-statement would put an admission of ignorance into the contract; the question it needs answering is a rule for the new service, and it comes back to this gate on the follow-up rather than to another archaeology run. Everything I have not named stands exactly as recovered and returns on ratify-notifications-1, D-notifications-13 among them, because whether the opt-in shortcut appears at every width is a G-DESIGN question and not mine to pre-empt. What would change this ruling is evidence that the citations do not hold — if the sender count or the reference-page count came out differently on a second reading, or if the four disclosing notices turned out to have a documented reason for addressing their recipients openly.

Conditions

  4. edit D-notifications-4: Every message the service sends comes from a single configured sender — a display name followed by one do-not-reply address, the same for every kind of message — and carries no reply-to address distinct from that sender.
  5. edit D-notifications-6: Every message the service sends ends with an offer labelled Unsubscribe, which opens the reader's own notification settings with the unsubscribe confirmation already asked.
  6. defect D-notifications-9: A notice sent to more than one person must hide every recipient from the others, carrying the batch as blind copies with the service's own address as the visible recipient, and this applies to the notices sent to an evaluation panel and to an opportunity's owner exactly as it does to every other multi-recipient notice.
  7. defect D-notifications-10: A message that the notification preference does not govern must not offer to unsubscribe; it links to the reader's notification settings without implying that any choice there will stop messages of that kind.
  8. defect D-notifications-14: A deactivated account receives no notification of any kind, including notices about opportunities it was watching, while the watch itself is retained so that reactivating the account restores it.
  9. defect D-notifications-16: The message announcing changed terms names every program whose proposals require a current acceptance — Code With Us, Sprint With Us and Team With Us — or names none of them rather than a subset.
  10. defect D-notifications-19: The administrator's notification reference page shows every message the service can send, so that no message exists which cannot be previewed there before the event that sends it.
  11. spike D-notifications-21: Must the service skip a recipient that holds no email address rather than composing a message addressed to nobody, and must a broadcast to many vendors always continue past such a recipient rather than being able to stop the run on one?
